# Cloudflare implementation references

This project uses Cloudflare-native services. The following implementation choices were checked against Cloudflare's official documentation on 2026-11-02.

- **Realtime TURN credentials:** generate short-lived ICE credentials server-side with `POST https://rtc.live.cloudflare.com/v1/turn/keys/{keyId}/credentials/generate-ice-servers`; keep the TURN key and API token on the Worker, and return only the `iceServers` payload to the browser. Each issued credential can carry a `customIdentifier` for per-user attribution. [Generate Credentials](https://developers.cloudflare.com/realtime/turn/generate-credentials/) · [Tag users with custom identifiers](https://developers.cloudflare.com/realtime/turn/replacing-existing/)
- **TURN analytics:** Cloudflare exposes Realtime TURN analytics through GraphQL (`https://api.cloudflare.com/client/v4/graphql`) and requires Account Analytics permission. Metrics include ingress/egress bytes, with `customIdentifier` filtering. Analytics are adaptively sampled and time-windowed; billing is based on egress bytes, so the dashboard explicitly labels values as estimates rather than exact live accounting. [Realtime TURN Analytics](https://developers.cloudflare.com/realtime/turn/analytics/) · [Sampling and customer usage guidance](https://developers.cloudflare.com/realtime/turn/replacing-existing/)
- **Durable Object signaling:** WebSocket Hibernation keeps client sockets connected while an object sleeps; per-socket attachments are used to restore identity/role after wake-up. Durable Objects carry signaling/control only; browser-to-browser WebRTC media uses the supplied STUN/TURN ICE servers. [Durable Object WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)
- **Durable Object class lifecycle:** for a new Worker, declare live classes using `durable_objects.bindings` and `exports` with `type: "durable-object"` and `storage: "sqlite"`. Do not mix the declarative `exports` flow with the legacy `migrations` array. [Durable Object class exports](https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/)
- **D1 migrations:** migrations are sequential `.sql` files under the configured directory; apply them using `wrangler d1 migrations apply <database-name> --remote`. Prefer a database name over a mutable binding name for deployment commands. [D1 Migrations](https://developers.cloudflare.com/d1/reference/migrations/)
- **Workers static assets:** Vite's `dist` directory can be configured with `assets.directory`; `binding` allows the Worker to fetch assets, `run_worker_first` routes `/api/*` through the Worker, and `not_found_handling: "single-page-application"` supports client-side routes. [Static assets configuration and bindings](https://developers.cloudflare.com/workers/static-assets/binding/)
- **GitHub Actions:** Cloudflare's documented CI/CD authentication uses `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` stored as GitHub Actions secrets; use the official `cloudflare/wrangler-action@v4` or Wrangler CLI in the workflow and scope the token to the required account and permissions. [GitHub Actions deployment](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/)
- **Cloudflare-native Git builds (optional):** Workers Builds can connect a GitHub repository to a Worker through the Builds API after the Cloudflare GitHub App is installed; the API uses a repository connection, Worker tag, build token UUID, and trigger configuration. This project keeps the direct GitHub Actions/Wrangler path as its documented deployment workflow. [Workers Builds](https://developers.cloudflare.com/workers/ci-cd/builds/) · [Builds API reference](https://developers.cloudflare.com/workers/ci-cd/builds/api-reference/)
- **Interactive Wrangler authorization:** `npx wrangler login --device` is a supported interactive OAuth device-authorization command for a human approving login; CI should instead use an API token. [Wrangler general commands](https://developers.cloudflare.com/workers/wrangler/commands/general/)

## Additional API contract checks

Cloudflare resource endpoint shapes and required permission labels were checked against Cloudflare’s official API schema: <https://api.cloudflare.com/client/v4/openapi.json>.

- D1 database listing and creation use `GET`/`POST /accounts/{account_id}/d1/database`; creation accepts `name` and an optional `primary_location_hint` (including `apac`). The schema labels the write permission `D1 Write`.
- KV namespace listing and creation use `GET`/`POST /accounts/{account_id}/storage/kv/namespaces`; creation accepts `title` and optional jurisdiction/mode. The schema labels the write permission `Workers KV Storage Write`.
- Worker module upload uses `PUT /accounts/{account_id}/workers/scripts/{script_name}`; Worker secret bindings use `PUT /accounts/{account_id}/workers/scripts/{script_name}/secrets`. The schema labels both writes `Workers Scripts Write`.
- TURN key management uses `/accounts/{account_id}/calls/turn_keys`; the schema labels read/write permissions `Calls Read` and `Calls Write`.

The initial Cloudflare environment now includes the newly created APAC `sparkcall-db` database with both checked-in migrations applied. No user records have been written. Cloudflare credentials remain outside the repository; the initial Worker/domain rollout is handled separately from the reusable GitHub Actions workflow.
